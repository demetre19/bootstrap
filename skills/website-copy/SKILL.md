# Website Copy

Write website copy that helps the intended visitor understand the page, trust it, and complete the right task.

Use the user's brief, approved strategy, verified evidence, and existing brand voice before applying these defaults. Never invent facts, proof, clients, results, prices, urgency, guarantees, or capabilities.

## Non-negotiable rules

- Give every page one main job.
- Write for the visitor's situation, not the organisation's internal structure.
- Make the first screen answer what this is, who it is for, why it matters, and what to do next.
- Use one primary action per page unless the page genuinely serves separate user paths.
- Prefer concrete situations, outcomes, and explanations over broad claims.
- Match every claim to available evidence.
- State material requirements, limitations, costs, and human handoffs clearly.
- Use familiar words and descriptive headings.
- Keep copy scannable without reducing it to fragments.
- Do not add pages, offers, features, or claims beyond the request.
- Do not write code or design specifications unless asked.
- Do not continue past an approval gate the user requested.

## Source hierarchy

Resolve conflicts in this order:

1. The user's current instruction
2. Approved website strategy or messaging
3. Verified business information and proof
4. Existing brand voice and page conventions
5. These general guidelines

Surface material conflicts. Do not blend incompatible claims or directions.

## Establish the assignment

Determine from the request and available materials:

- Scope: one page, selected pages, or a complete website
- Website type
- Intended visitor
- Visitor awareness and traffic source when relevant
- Visitor problem, question, or goal
- Page or website purpose
- Primary action
- Available proof
- Brand voice
- Legal, compliance, geographic, or industry constraints
- Required output format

Read supplied files and existing website materials before asking questions. Ask only when missing information would materially change the promise, audience, architecture, proof, or primary action. Otherwise proceed with explicit assumptions.

## Workflow for a single page

1. Write a one-sentence page job.
2. Identify the visitor, arrival context, main question, doubts, and desired next step.
3. Select the shortest structure that completes the job.
4. Draft the first screen.
5. Draft the supporting sections.
6. Add only verified proof and necessary boundaries.
7. Close by confirming the outcome and giving one clear next step.
8. Run the self-review.

### General page sequence

Use for informational, support, policy, documentation, application, and similar pages:

1. Orientation
2. Relevance
3. Necessary details
4. Method, source, or evidence
5. Requirements, limitations, or exceptions
6. Next step

### Commercial page sequence

Use when the page must help a suitable visitor decide or enquire:

1. Problem or desired outcome
2. Plain-language explanation
3. Recognisable situation
4. Value and benefits
5. Method
6. Proof
7. Boundaries and objections
8. Primary action

Do not force every page into the commercial sequence. The page job controls the structure.

## Workflow for a complete website

### Create the messaging foundation

Define the primary audience, central problem or outcome, value proposition, main promise and evidence, brand voice, primary action, objections, boundaries, and repeated language.

### Create the page architecture

For each page, state its name, URL when requested, visitor, one-sentence job, primary action, proof requirements, and relationship to other pages.

Keep navigation and page count as small as the website's real jobs allow. Create a separate page only when the audience, purpose, promise, proof, or next action is genuinely different.

### Draft pages in journey order

Draft the pages that establish the core message first, then offers or tasks, proof, process, trust, contact or conversion routes, and utility pages. Adapt the order to the website type. Do not draft thin pages merely to fill a sitemap.

### Check the complete system

Confirm that navigation is familiar, every page has one job, pages do not compete or duplicate, claims and terminology stay consistent, and each visitor has a sensible next route.

## First-screen standard

The first screen should normally contain:

1. A clear page or category label
2. One descriptive, pain-led, or outcome-led headline
3. A short explanation of the value or purpose
4. One primary action or obvious route forward
5. One relevant trust cue when approved evidence exists

The first screen does not always need to sell. It always needs to orient.

Avoid multiple primary actions, unexplained jargon, vague growth claims, long introductions, and unapproved proof.

## Copy standards

- Lead with the visitor's problem, question, task, or desired outcome.
- Use active voice and natural sentence rhythm.
- Prefer specific nouns and verbs.
- Explain technology through what it helps accomplish.
- Use short headlines when clarity allows.
- Make headings meaningful when scanned alone.
- Use verb-first button labels that describe the result of clicking.
- Keep one idea per paragraph or section.
- Repeat central language deliberately across the journey.
- Remove filler, hype, clichés, and unsupported superlatives.
- Avoid generic AI-copy vocabulary.
- Do not use em dashes or en dashes.
- Do not make visitors diagnose which product they need when the organisation should guide them.

## Proof and claims

Classify evidence accurately:

- **Example:** An illustration of a possible use
- **Demonstration:** A controlled display of behaviour
- **Capability:** Something a product or system can do
- **Implementation:** Something that has been built or installed
- **Measured outcome:** A verified result with an identified measurement method

Never present one category as another. Do not use names, logos, quotations, screenshots, recordings, statistics, or outcomes without permission and source verification.

When proof is unavailable, write an explicit proof requirement or explain the method and boundaries. Never fabricate a substitute.

## Forms and interactive features

When writing for a form, chatbot, calculator, questionnaire, configurator, search tool, or agent, make clear its purpose, immediate value, necessary input, next step, states, human handoff, consent, privacy, and material provider or cost boundaries.

Do not make an interactive feature sound more capable than its verified behaviour.

## Output format

Unless the user requests copy only, start with a compact editorial block:

```markdown
Page job:
Intended visitor:
Visitor state or traffic context:
Primary action:
Proof available or required:
Assumptions:
```

Then provide publishable copy separately. For a complete website, provide the messaging foundation and page architecture before page drafts unless already approved. If the user requests staged approval, stop at each gate.

Do not mix editorial notes into publishable copy. Clearly mark placeholders and proof requirements.

## Self-review

Before delivery, verify:

- Can the intended visitor identify the subject and relevance quickly?
- Is the page job clear and fully served?
- Is the primary action obvious and accurate?
- Does the opening reflect the visitor's real situation?
- Is every claim supported or qualified?
- Are proof categories represented honestly?
- Are limitations visible where they affect a decision?
- Can headings be understood when scanned alone?
- Is the copy coherent on a small screen?
- Does the ending confirm the outcome and next step?
- For a full website, do navigation, terminology, promises, and actions remain consistent?
- Has filler, generic AI wording, and forbidden dash punctuation been removed?

Revise until every applicable check passes. Deliver the finished draft, not the critique.
